# π₀.₅ (Pi05) Policy

π₀.₅ is a **Vision-Language-Action model with open-world generalization**, from Physical Intelligence. The LeRobot implementation is adapted from their open source [OpenPI](https://github.com/Physical-Intelligence/openpi) repository.

## Model Overview

π₀.₅ represents a significant evolution from π₀, developed by [Physical Intelligence](https://www.physicalintelligence.company/blog/pi05) to address a big challenge in robotics: **open-world generalization**. While robots can perform impressive tasks in controlled environments, π₀.₅ is designed to generalize to entirely new environments and situations that were never seen during training.

### The Generalization Challenge

As Physical Intelligence explains, the fundamental challenge isn't performing tasks of agility or dexterity, but generalization, the ability to correctly perform tasks in new settings with new objects. Consider a robot cleaning different homes: each home has different objects in different places. Generalization must occur at multiple levels:

- **Physical Level**: Understanding how to pick up a spoon (by the handle) or plate (by the edge), even with unseen objects in cluttered environments
- **Semantic Level**: Understanding task semantics, where to put clothes and shoes (laundry hamper, not on the bed), and what tools are appropriate for cleaning spills
- **Environmental Level**: Adapting to "messy" real-world environments like homes, grocery stores, offices, and hospitals

### Co-Training on Heterogeneous Data

The breakthrough innovation in π₀.₅ is **co-training on heterogeneous data sources**. The model learns from:

1. **Multimodal Web Data**: Image captioning, visual question answering, object detection
2. **Verbal Instructions**: Humans coaching robots through complex tasks step-by-step
3. **Subtask Commands**: High-level semantic behavior labels (e.g., "pick up the pillow" for an unmade bed)
4. **Cross-Embodiment Robot Data**: Data from various robot platforms with different capabilities
5. **Multi-Environment Data**: Static robots deployed across many different homes
6. **Mobile Manipulation Data**: ~400 hours of mobile robot demonstrations

This diverse training mixture creates a "curriculum" that enables generalization across physical, visual, and semantic levels simultaneously.

## Usage

To use π₀.₅ in your LeRobot configuration, specify the policy type as:

```python
policy.type=pi05
```

## Training

### Training Command Example

Here's a complete training command for finetuning the base π₀.₅ model on your own dataset:

```bash
lerobot-train \
    --dataset.repo_id=your_dataset \
    --policy.type=pi05 \
    --output_dir=./outputs/pi05_training \
    --job_name=pi05_training \
    --policy.repo_id=your_repo_id \
    --policy.pretrained_path=lerobot/pi05_base \
    --policy.compile_model=true \
    --policy.gradient_checkpointing=true \
    --wandb.enable=true \
    --policy.dtype=bfloat16 \
    --policy.freeze_vision_encoder=false \
    --policy.train_expert_only=false \
    --steps=3000 \
    --policy.device=cuda \
    --batch_size=32
```

By default, a fresh flow run first performs 500 action-only flow-inpainting updates, then performs
the requested `--steps` observation-conditioned flow updates. For a complete 50-action chunk,
Stage 1 randomly masks 40 valid positions without replacement, keeps 10 clean actions as
bidirectional context, and predicts flow velocity only at the masked positions. If a padded chunk
has fewer than 40 valid positions, all of its valid positions are masked. Stage 1 trains the complete
action path (the action expert, input/output projections, and timestep MLP) while the VLM and the
legacy inpainting role embedding remain frozen. No temporary prediction head is created or
discarded. After Stage 1, Stage 2 rebuilds the policy with the observation-conditioned flow
configuration and unfreezes the complete VLM, including the vision encoder, unless the user
explicitly overrides the corresponding finetuning flags.

Set `--policy.next_action_pretrain_steps=0` to skip Stage 1. The compatibility name
`training_stage=next_action` now denotes action-only flow inpainting rather than the former 25-to-25
MSE regression objective. The mask size and optional full-mask fraction can be changed with
`--policy.next_action_masked_steps` and `--policy.next_action_full_mask_probability`.
The legacy `next_action_context_steps` and `next_action_prediction_steps` fields are accepted only
for loading older checkpoints and no longer affect training.

### Key Training Parameters

- **`--policy.compile_model=true`**: Enables model compilation for faster training
- **`--policy.gradient_checkpointing=true`**: Reduces memory usage significantly during training
- **`--policy.dtype=bfloat16`**: Use mixed precision training for efficiency
- **`--batch_size=32`**: Batch size for training, adapt this based on your GPU memory
- **`--policy.pretrained_path=lerobot/pi05_base`**: The base π₀.₅ model you want to finetune, options are:
  - [lerobot/pi05_base](https://huggingface.co/lerobot/pi05_base)
  - [lerobot/pi05_libero](https://huggingface.co/lerobot/pi05_libero) (specifically trained on the Libero dataset)

### Training Parameters Explained

Fresh π₀.₅ configurations use one AdamW learning rate for all trainable VLM and action-side
parameters. After warmup, the learning rate follows a cosine decay from `2.5e-5` to a floor of
`1e-5`. Loading or resuming a checkpoint preserves the optimizer values saved in that checkpoint.
The integrated Stage 1 uses a fixed `2.5e-5` peak learning rate and `1e-5` decay floor, matching the
fresh Stage 2 defaults. Its optimizer state is not carried into Stage 2. During an integrated
two-stage run, Stage 2 saves a checkpoint every 3,000 updates when checkpointing is enabled, and
once more at the final update when the total step count is not divisible by 3,000.

Without CABO, gradient clipping is policy-specific. The action-side gradient RMS is capped at 10
times the VLM gradient RMS, and only action-side gradients are rescaled when that cap is exceeded.
VLM gradients are left unchanged, and global gradient clipping is disabled. CABO is enabled by
default and disables this action-gradient hook so that only the relative-update controller is active.
Training checkpoints are saved every 10,000 steps by default and once more at the final step.

PI0.5 also provides relative-update optimizer control (CABO). Before each AdamW step, CABO
deterministically computes the candidate learning update for three parameter groups: VLM, action
expert, and action projections. The VLM update remains at full scale. After an initial warmup, CABO
only reduces the two action-side learning rates when their parameter-relative updates are too large
compared with the VLM update:

```bash
lerobot-train \
    ... \
    --policy.cabo_enabled=true \
    --policy.cabo_expert_update_ratio=2.0 \
    --policy.cabo_projection_update_ratio=5.0 \
    --policy.cabo_vlm_update_ema_decay=0.95 \
    --policy.cabo_update_warmup_steps=100 \
    --policy.cabo_vlm_update_floor_ratio=0.1
```

For a group `g`, let its candidate AdamW learning update be `delta_g`. CABO measures

`r_g = ||delta_g||_2 / ||theta_g||_2`.

Only parameters with a gradient participate. Decoupled weight decay is excluded from `delta_g`, so
weight decay cannot be mistaken for a VLM learning signal. CABO maintains an exponential moving
average `r_vlm_ref` of the VLM rate and applies the following scales after warmup:

`s_expert = min(1, cabo_expert_update_ratio * r_vlm_ref / r_expert)`

`s_projection = min(1, cabo_projection_update_ratio * r_vlm_ref / r_projection)`

The reference is floored at `cabo_vlm_update_floor_ratio` times the average VLM rate observed during
warmup. This prevents a transient near-zero VLM update from permanently starving the action head.
Both action scales are exactly `1` during warmup and are never greater than `1`, so CABO attenuates
action learning but never amplifies it. The policy-specific action-gradient clipping hook is disabled
while CABO is enabled to avoid applying two overlapping controllers.

CABO adds no model forward pass, action-space probe, random projection, or Jacobian-vector product.
It derives the next update directly from the current gradients and AdamW state without mutating that
state. With low-precision parameters, the full-scale candidate uses the native parameter dtype; the
learning-rate scale is then applied by the real optimizer step.

CABO currently supports single-device and DDP training, but not FSDP. In DDP, every rank participates
in the aggregate squared update and parameter norms. It requires both the VLM and action side to be
trainable, so it cannot be combined with `train_expert_only=true`. CABO also requires the policy
training preset and its three named AdamW parameter groups. Enable it in a new run initialized from
model weights; an older single-group or two-group optimizer checkpoint cannot be resumed directly
with this layout. A non-finite training gradient or candidate update causes all ranks to skip the
complete optimizer and scheduler step without advancing the CABO controller state.

| Parameter                       | Default  | Description                                                |
| ------------------------------- | -------- | ---------------------------------------------------------- |
| `optimizer_lr`                  | `2.5e-5` | Unified AdamW learning rate for VLM and action parameters   |
| `scheduler_decay_lr`            | `1e-5`   | Learning-rate floor after cosine decay                      |
| `save_freq`                     | `10000`  | Save every 10,000 steps and always save the final checkpoint |
| `clip_action_head_by_vlm`       | `true`   | Enable the action-side RMS cap                              |
| `action_head_grad_clip_ratio`   | `10.0`   | Enforce `action_rms <= 10 * vlm_rms`                        |
| `optimizer_grad_clip_norm`      | `0.0`    | Disable global gradient clipping                            |
| `cabo_enabled`                  | `true`   | Enable deterministic relative-update control                |
| `cabo_expert_update_ratio`      | `2.0`    | Limit expert rate to this multiple of the VLM reference      |
| `cabo_projection_update_ratio`  | `5.0`    | Limit projection rate to this multiple of the VLM reference  |
| `cabo_vlm_update_ema_decay`     | `0.95`   | EMA decay used for the VLM relative-update reference         |
| `cabo_update_warmup_steps`      | `100`    | Steps that collect the reference without action attenuation  |
| `cabo_vlm_update_floor_ratio`   | `0.1`    | Warmup-average fraction used as the VLM reference floor      |
| `freeze_vision_encoder`         | `false`  | Do not freeze the vision encoder                            |
| `train_expert_only`             | `false`  | Do not freeze the VLM; train all parameters                 |

**💡 Tip**: Setting `train_expert_only=true` freezes the VLM and trains only the action expert and
projections, allowing finetuning with reduced memory usage. Because CABO needs trainable VLM
parameters, also set `cabo_enabled=false` for expert-only training.

If your dataset is not converted with `quantiles`, you can convert it with the following command:

```bash
python src/lerobot/scripts/augment_dataset_quantile_stats.py \
    --repo-id=your_dataset \
```

Or train pi05 with this normalization mapping: `--policy.normalization_mapping='{"ACTION": "MEAN_STD", "STATE": "MEAN_STD", "VISUAL": "IDENTITY"}'`

## Relative Actions

By default, π₀.₅ predicts absolute actions. You can enable **relative actions** so the model predicts offsets relative to the current robot state. This can improve training stability for certain setups.

To use relative actions, first recompute your dataset stats in relative space via the CLI:

```bash
lerobot-edit-dataset \
    --repo_id your_dataset \
    --operation.type recompute_stats \
    --operation.relative_action true \
    --operation.chunk_size 50 \
    --operation.relative_exclude_joints "['gripper']" \
    --push_to_hub true
```

Or equivalently in Python:

```python
from lerobot.datasets import LeRobotDataset, recompute_stats

dataset = LeRobotDataset("your_dataset")
recompute_stats(dataset, relative_action=True, chunk_size=50, relative_exclude_joints=["gripper"])
dataset.push_to_hub()
```

The `chunk_size` should match your policy's `chunk_size` (default 50 for π₀.₅). `relative_exclude_joints` lists joint names that should remain in absolute space (e.g. gripper commands). Use `--push_to_hub true` to upload the updated stats to the Hub.

Then train with relative actions enabled:

```bash
lerobot-train \
    --dataset.repo_id=your_dataset \
    --policy.type=pi05 \
    --policy.use_relative_actions=true \
    --policy.relative_exclude_joints='["gripper"]' \
    ...
```

## Performance Results

### Libero Benchmark Results

π₀.₅ has demonstrated strong performance on the Libero benchmark suite. To compare and test its LeRobot implementation, we finetuned the libero base model for an additional 6k steps on the Libero dataset and compared the results to the OpenPI reference results.

| Benchmark          | LeRobot Implementation | OpenPI Reference |
| ------------------ | ---------------------- | ---------------- |
| **Libero Spatial** | 97.0%                  | 98.8%            |
| **Libero Object**  | 99.0%                  | 98.2%            |
| **Libero Goal**    | 98.0%                  | 98.0%            |
| **Libero 10**      | 96.0%                  | 92.4%            |
| **Average**        | 97.5%                  | 96.85%           |

These results demonstrate π₀.₅'s strong generalization capabilities across diverse robotic manipulation tasks. To reproduce these results, you can follow the instructions in the [Libero](https://huggingface.co/docs/lerobot/libero) section.
