# π₀.₅ (Pi05) Policy

π₀.₅ is a **Vision-Language-Action model with open-world generalization**, from Physical Intelligence. The LeRobot implementation is adapted from their open source [OpenPI](https://github.com/Physical-Intelligence/openpi) repository.

## Model Overview

π₀.₅ represents a significant evolution from π₀, developed by [Physical Intelligence](https://www.physicalintelligence.company/blog/pi05) to address a big challenge in robotics: **open-world generalization**. While robots can perform impressive tasks in controlled environments, π₀.₅ is designed to generalize to entirely new environments and situations that were never seen during training.

### The Generalization Challenge

As Physical Intelligence explains, the fundamental challenge isn't performing tasks of agility or dexterity, but generalization, the ability to correctly perform tasks in new settings with new objects. Consider a robot cleaning different homes: each home has different objects in different places. Generalization must occur at multiple levels:

- **Physical Level**: Understanding how to pick up a spoon (by the handle) or plate (by the edge), even with unseen objects in cluttered environments
- **Semantic Level**: Understanding task semantics, where to put clothes and shoes (laundry hamper, not on the bed), and what tools are appropriate for cleaning spills
- **Environmental Level**: Adapting to "messy" real-world environments like homes, grocery stores, offices, and hospitals

### Co-Training on Heterogeneous Data

The breakthrough innovation in π₀.₅ is **co-training on heterogeneous data sources**. The model learns from:

1. **Multimodal Web Data**: Image captioning, visual question answering, object detection
2. **Verbal Instructions**: Humans coaching robots through complex tasks step-by-step
3. **Subtask Commands**: High-level semantic behavior labels (e.g., "pick up the pillow" for an unmade bed)
4. **Cross-Embodiment Robot Data**: Data from various robot platforms with different capabilities
5. **Multi-Environment Data**: Static robots deployed across many different homes
6. **Mobile Manipulation Data**: ~400 hours of mobile robot demonstrations

This diverse training mixture creates a "curriculum" that enables generalization across physical, visual, and semantic levels simultaneously.

## Training

### Trainable prompts with a frozen VLM

This repository's π₀.₅ variant inserts trainable prompt embeddings between the VLM prefix and the
action tokens: `[VLM tokens] [prompt tokens] [action tokens]`. The default is 16 prompts, initialized
from a normal distribution with standard deviation `0.02`. They use the action expert's embedding
width and are processed by the action expert. Set `--policy.num_prompt_tokens=0` for an ablation
without prompts; the VLM stays frozen.

Attention has three blocks. VLM tokens attend only to the VLM prefix. Prompts attend to the VLM
prefix and all prompts. Action tokens attend to the VLM prefix, prompts, and all action tokens.
During action-only Stage 1, the VLM prefix is absent and the prompt/action blocks remain. During
inference, the frozen VLM prefix is cached and prompts are processed with the action tokens on every
denoising step. Prompt outputs are not returned as actions, so the action chunk length is unchanged.

The complete VLM, including its vision encoder, remains frozen throughout Stage 1, the
observation-conditioned bridge, and Stage 2. Both `freeze_vision_encoder` and `train_expert_only`
are enforced as `true`, including when loading older configurations that set them to `false`.
Trainable parameters are the prompts and the complete action path: the action expert, input/output
projections, and timestep MLP.

### Training Command Example

Here's a complete training command for finetuning the base π₀.₅ model on your own dataset:

```bash
lerobot-train \
    --dataset.repo_id=your_dataset \
    --policy.type=pi05 \
    --output_dir=./outputs/pi05_training \
    --job_name=pi05_training \
    --policy.repo_id=your_repo_id \
    --policy.pretrained_path=lerobot/pi05_base \
    --policy.compile_model=true \
    --policy.gradient_checkpointing=true \
    --wandb.enable=true \
    --policy.dtype=bfloat16 \
    --policy.num_prompt_tokens=16 \
    --policy.freeze_vision_encoder=true \
    --policy.train_expert_only=true \
    --steps=3000 \
    --policy.device=cuda \
    --batch_size=32
```

By default, a fresh flow run first performs a 1,000-update Stage 1, then performs the requested
`--steps` observation-conditioned Stage 2 updates. The first 750 Stage 1 updates use action-only
flow inpainting. For a complete 50-action chunk, they randomly mask 40 valid positions without
replacement, keep 10 clean actions as bidirectional context, and predict flow velocity only at the
masked positions. If a padded chunk has fewer than 40 valid positions, all of its valid positions are
masked. The final 250 Stage 1 updates form a bridge to Stage 2: they use the same
observation-conditioned full-flow loss as Stage 2, while the VLM remains frozen. Both Stage 1
objectives train the prompts and complete action path (the action expert, input/output projections,
and timestep MLP) and share one uninterrupted optimizer and learning-rate schedule. The legacy
inpainting role embedding remains frozen, and no temporary prediction head is created or discarded.

After Stage 1, Stage 2 rebuilds the policy and optimizer with the formal flow configuration, keeps
the VLM frozen, and continues training the prompts and complete action path from their Stage 1
weights. Optional CABO learning-rate attenuation uses the prompt update as its reference and applies
throughout Stage 1, the bridge, and Stage 2. VLM-relative action-gradient clipping remains disabled
because the frozen VLM provides no gradient reference.
Set `--policy.next_action_bridge_steps=0` to keep all Stage 1 updates
action-only, or change it to adjust the bridge length; it must not exceed
`next_action_pretrain_steps`. The bridge is enabled by the integrated two-stage run only, so a
standalone `training_stage=next_action` invocation retains its original all-inpainting behavior.

Set `--policy.next_action_pretrain_steps=0` to skip Stage 1; in that case the bridge setting is
ignored. The compatibility name
`training_stage=next_action` denotes the frozen-VLM Stage 1; its base objective is action-only flow
inpainting rather than the former 25-to-25 MSE regression objective, and the integrated trainer
overrides it with full flow during the configured bridge. The mask size and optional full-mask
fraction can be changed with `--policy.next_action_masked_steps` and
`--policy.next_action_full_mask_probability`.
The legacy `next_action_context_steps` and `next_action_prediction_steps` fields are accepted only
for loading older checkpoints and no longer affect training.

### Key Training Parameters

- **`--policy.compile_model=true`**: Enables model compilation for faster training
- **`--policy.gradient_checkpointing=true`**: Reduces memory usage significantly during training
- **`--policy.dtype=bfloat16`**: Use mixed precision training for efficiency
- **`--policy.num_prompt_tokens=16`**: Number of trainable embeddings before the action tokens
- **`--policy.cabo_enabled=true --policy.cabo_prompt_update_ratio=1.0`**: Keep the prompt's relative
  learning update at least as large as each part of the action branch in every training stage
- **`--policy.train_expert_only=true`**: Enforced in this variant; the entire VLM stays frozen
- **`--batch_size=32`**: Batch size for training, adapt this based on your GPU memory
- **`--policy.pretrained_path=lerobot/pi05_base`**: The base π₀.₅ model you want to finetune, options are:
  - [lerobot/pi05_base](https://huggingface.co/lerobot/pi05_base)
  - [lerobot/pi05_libero](https://huggingface.co/lerobot/pi05_libero) (specifically trained on the Libero dataset)

### Training Parameters Explained

Fresh π₀.₅ configurations use one scheduled AdamW learning rate for all trainable prompt and action-side
parameters. After warmup, the learning rate follows a cosine decay from `2.5e-5` to a floor of
`1e-5`. Compatible checkpoint resumes preserve their saved optimizer state and settings.
The integrated Stage 1 uses a fixed `2.5e-5` peak learning rate and `1e-5` decay floor, matching the
fresh Stage 2 defaults. Its optimizer and scheduler continue across the inpainting-to-bridge
boundary, but their state is not carried into Stage 2. During an integrated two-stage run, Stage 2
saves a checkpoint every 3,000 updates when checkpointing is enabled, and once more at the final
update when the total step count is not divisible by 3,000.

Global gradient clipping is disabled by default (`optimizer_grad_clip_norm=0.0`); prompts and the
action path use the full scheduled AdamW learning rate when CABO is disabled.
`clip_action_head_by_vlm` must remain `false` for flow training because it requires a trainable VLM.

Enable the prompt-based CABO controller by adding:

```bash
--policy.cabo_enabled=true \
--policy.cabo_prompt_update_ratio=1.0
```

For each optimizer group, CABO measures the proposed AdamW learning update relative to its parameter
norm: `r = ||delta_theta|| / ||theta||`. This measurement includes the scheduled learning rate and
AdamW moment preconditioning, but excludes weight decay. The prompt group keeps its full scheduled
learning rate. CABO reduces the current step's learning rate of each action group as needed so that
`r_prompt >= cabo_prompt_update_ratio * r_action`. The action groups cover the complete trainable
action branch: the action expert and the input/output projections plus timestep MLP. This also
bounds the combined action branch's relative learning update. The default ratio `1.0` means at least
the same relative update, including equality; larger ratios make the constraint stronger.

If the prompt has no learning update, CABO gives any moving action group a zero learning rate for
that step. Scaled candidates are checked again in the parameter's native precision; further backoff
prevents floating-point rounding from exceeding the limit. This adds optimizer-side computation
without another model forward pass.

CABO is disabled by default and requires `num_prompt_tokens > 0` when enabled. It applies from the
first optimizer update in action-only Stage 1, the observation-conditioned bridge, and Stage 2.
There is no CABO warmup, EMA, or reference floor. The old `cabo_expert_update_ratio`,
`cabo_projection_update_ratio`, `cabo_vlm_update_ema_decay`, `cabo_update_warmup_steps`, and
`cabo_vlm_update_floor_ratio` fields remain loadable for compatibility but no longer affect CABO.
The normal learning-rate scheduler still uses its configured warmup. The VLM stays frozen and is
excluded from the optimizer. CABO supports single-device and DDP training; FSDP is unsupported.

| Parameter                    | Default  | Description                                                        |
| ---------------------------- | -------- | ------------------------------------------------------------------ |
| `num_prompt_tokens`           | `16`     | Trainable prompts between VLM and action tokens; `0` disables them  |
| `prompt_init_std`             | `0.02`   | Standard deviation for new prompt embeddings                        |
| `next_action_pretrain_steps`  | `1000`   | Total Stage 1 updates before formal Stage 2                          |
| `next_action_bridge_steps`    | `250`    | Final Stage 1 updates using frozen-VLM full-flow                     |
| `optimizer_lr`               | `2.5e-5` | AdamW learning rate for prompts and action parameters                |
| `scheduler_decay_lr`         | `1e-5`   | Learning-rate floor after cosine decay                               |
| `save_freq`                  | `10000`  | General trainer default; integrated Stage 2 saves every 3,000 steps |
| `clip_action_head_by_vlm`    | `false`  | Must be disabled for flow training with the frozen VLM               |
| `optimizer_grad_clip_norm`   | `0.0`    | Disable global gradient clipping                                    |
| `cabo_enabled`               | `false`  | Cap action learning updates relative to the prompt in all stages     |
| `cabo_prompt_update_ratio`   | `1.0`    | Minimum prompt/action relative learning-update ratio; must be >= 1   |
| `freeze_vision_encoder`      | `true`   | Enforced: keep the vision encoder frozen                             |
| `train_expert_only`          | `true`   | Enforced: freeze the VLM; train prompts and the action path          |

### Loading existing checkpoints

Base π₀.₅ checkpoints and older full-model checkpoints without prompt weights initialize new prompts
using `num_prompt_tokens` and `prompt_init_std`. Checkpoints saved by this variant include the
prompt embeddings, so loading them preserves the learned prompts. Keep the saved prompt count when
continuing a trained prompt checkpoint.

When moving an older training run to this variant, start a new run with
`--policy.pretrained_path=/path/to/pretrained_model`. An old optimizer state may have a different
parameter layout because prompts were added and VLM parameters are now frozen; it may not support
direct `--resume=true`. Enabling CABO also changes the optimizer layout to named `prompt`,
`action_expert`, and `action_projection` groups. When enabling it for an existing non-CABO run, or
migrating an older VLM-based CABO run, initialize a new optimizer from the saved model weights
with `--policy.pretrained_path`; direct resume requires the same optimizer group layout.
Older configurations must set `--policy.clip_action_head_by_vlm=false` for flow training.

Older PEFT adapters that do not save `prompt_tokens` cannot be loaded with prompts enabled. Use a
prompt-enabled adapter, start from a full-model checkpoint, or set `num_prompt_tokens=0` for the
legacy adapter ablation.

If your dataset is not converted with `quantiles`, you can convert it with the following command:

```bash
python src/lerobot/scripts/augment_dataset_quantile_stats.py \
    --repo-id=your_dataset \
```

Or train pi05 with this normalization mapping: `--policy.normalization_mapping='{"ACTION": "MEAN_STD", "STATE": "MEAN_STD", "VISUAL": "IDENTITY"}'`

## Relative Actions

By default, π₀.₅ predicts absolute actions. You can enable **relative actions** so the model predicts offsets relative to the current robot state. This can improve training stability for certain setups.

To use relative actions, first recompute your dataset stats in relative space via the CLI:

```bash
lerobot-edit-dataset \
    --repo_id your_dataset \
    --operation.type recompute_stats \
    --operation.relative_action true \
    --operation.chunk_size 50 \
    --operation.relative_exclude_joints "['gripper']" \
    --push_to_hub true
```

Or equivalently in Python:

```python
from lerobot.datasets import LeRobotDataset, recompute_stats

dataset = LeRobotDataset("your_dataset")
recompute_stats(dataset, relative_action=True, chunk_size=50, relative_exclude_joints=["gripper"])
dataset.push_to_hub()
```

The `chunk_size` should match your policy's `chunk_size` (default 50 for π₀.₅). `relative_exclude_joints` lists joint names that should remain in absolute space (e.g. gripper commands). Use `--push_to_hub true` to upload the updated stats to the Hub.

Then train with relative actions enabled:

```bash
lerobot-train \
    --dataset.repo_id=your_dataset \
    --policy.type=pi05 \
    --policy.use_relative_actions=true \
    --policy.relative_exclude_joints='["gripper"]' \
    ...
```

## Performance Results

### Libero Benchmark Results

The following results describe the upstream LeRobot π₀.₅ implementation. They have not been
re-measured for this repository's frozen-VLM prompt variant.

π₀.₅ has demonstrated strong performance on the Libero benchmark suite. To compare and test its LeRobot implementation, we finetuned the libero base model for an additional 6k steps on the Libero dataset and compared the results to the OpenPI reference results.

| Benchmark          | LeRobot Implementation | OpenPI Reference |
| ------------------ | ---------------------- | ---------------- |
| **Libero Spatial** | 97.0%                  | 98.8%            |
| **Libero Object**  | 99.0%                  | 98.2%            |
| **Libero Goal**    | 98.0%                  | 98.0%            |
| **Libero 10**      | 96.0%                  | 92.4%            |
| **Average**        | 97.5%                  | 96.85%           |

These results demonstrate π₀.₅'s strong generalization capabilities across diverse robotic manipulation tasks. To reproduce these results, you can follow the instructions in the [Libero](https://huggingface.co/docs/lerobot/libero) section.
